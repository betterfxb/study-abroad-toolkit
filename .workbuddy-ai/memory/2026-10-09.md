### 诊断经验（避免重复踩坑）
- **FastAPI 0.143 的 `app.routes` 不再平铺子路由**，子路由被包成 `_IncludedRouter`，直接遍历 `app.routes` 会误判「路由没注册」。核对路由应使用 `app.openapi()['paths']`。

   - 抽了公共依赖 `app/api/deps.py`（get_db，无库→503），admin.py 改为复用
2. **ORM 跨方言化** `app/models.py`：`JSONType = JSON().with_variant(JSONB,"postgresql")`、`BigIntPK = BigInteger().with_variant(Integer,"sqlite")`。PG 行为不变（仍 BIGSERIAL/JSONB），SQLite 可跑端到端。
3. **全链路脚本** `scripts/jobs_flow.py`：采集→入库→查询→导出汇总表，支持 `--dsn` 指向 PG，默认 SQLite。
4. **端到端测试** `tests/e2e_jobs_test.py`：39 项，SQLite 落地，覆盖入库/幂等/筛选/分页/排序/聚合/CSV/HTTP 接口（含 404/422）。

### 本轮修掉的 2 个真实缺陷（端到端测试立即暴露）
1. **`deadline` 类型不匹配**：抽取层输出 ISO 字符串，但列是 DATE。PG 靠隐式转换侥幸通过，SQLite 直接 TypeError。修复：落库边界显式 `_to_date()`/`_to_float()`，保持抽取层对外契约不变。
2. **单条坏数据污染整批**：一条 flush 失败后 Session 进入待回滚态，后续全部连带失败（实测 4 篇只入库 1 篇）。修复：`SqlRepository.item_scope()` 用 SAVEPOINT 包裹每条记录，Pipeline 逐条隔离。

- 冒烟 90/90（无回归）、端到端 39/39、抽取对比 78.2%（无回归）
- 路由 19 个（`app.openapi()['paths']`）
- 全链路实测：3 篇→4 岗位；第二轮复用同库 → 0 新增 / 3 判重（幂等生效）
- 装了 `psycopg 3.3.6`（requirements 里本就有 `psycopg[binary]>=3.2`）

## 第 11 轮 · 主网关：api-gateway（NestJS + node:sqlite）

### 目标
补齐契约里已定义但未实现的业务接口（`/auth`、`/profile`、`/documents`、`/resumes`、`/applications`、`/subscriptions`），并把 crawler-service 与 intelligence-service 收敛到同一 Base URL 之下。

### 关键技术决策
1. **持久层用 Node 内置 `node:sqlite`**（`--experimental-sqlite`）——**零原生依赖**，避免 better-sqlite3 在 Windows 上需要编译工具链。业务层只调仓储方法，生产切 PostgreSQL 时替换 `DatabaseService` 即可。
2. **Express 5 通配符**：NestJS 11 默认 Express 5，中间件路由 `'*'` 已失效，必须用 `'{*splat}'`。
3. **Nest DI 陷阱**：`DatabaseService` 构造函数不能带「有默认值的普通参数」，否则 Nest 尝试注入该参数报 `UnknownDependenciesException`。改为无参构造 + 在 `onModuleInit` 读 `process.env`。
4. **代理统一归一化**：上游已封装（intelligence，含 code）取其 `data`；上游裸对象（crawler /jobs）整体作为 `data`；`trace_id` 一律换成网关自己的。

### 交付（8 组接口 + 代理）
- **Auth**：注册/登录/刷新/登出；bcrypt 哈希；access 2h / refresh 30d；**refresh 轮换**（旧 token 即吊销，防重放）；支持 `Bearer` 与 `X-Ext-Token` 双凭证。
- **Profile**：GET/PUT/PATCH，PATCH 实现 **JSON Merge Patch (RFC 7396)**（递归合并 / null 删键 / 数组替换）+ 顶层字段白名单。
- **Documents**：presign（校验 doc_type + 20MB 上限）/ 登记 / 列表 / 删除；**简历启发式解析**（抽邮箱/手机/学历/技能，标注 `method: heuristic`）+ 版本管理。
- **Applications**：院校（8 条种子）/ 申请（按 institution_id 自动带出信息）/ 推荐人 + invite 状态跟踪（**不代发邮件**）。
- **Subscriptions**：CRUD，`keywords`/`cities` 兼容数组与逗号分隔字符串。
- **Proxy**：`/api/v1/jobs*` → crawler、`/ext/v1/*` → intelligence、`/api/v1/meta/services` 健康聚合。
- **横切**：响应统一封装拦截器、异常过滤器（错误码映射）、trace_id 中间件、幂等拦截器（Idempotency-Key，24h）、分页/排序解析（白名单防注入）。

### 本轮修掉的 3 个真实缺陷
1. **`_sync_url` 不处理 SQLite 异步方言**（crawler-service）：`get_session_factory` 用同步引擎，但 `_sync_url` 只重写 PostgreSQL，导致 `sqlite+aiosqlite://` 被透传给同步 `create_engine` → `MissingGreenlet`。修复：`sqlite+aiosqlite://` → `sqlite://`。
2. **代理丢失 UTF-8 BOM**：Node 的 `fetch().text()` 按 WHATWG 规范**自动剥离 BOM**，导致 CSV 导出经网关后 Excel 打开乱码。修复：非 JSON 响应改用 `arrayBuffer()` + `Buffer.toString('utf8')`，并发送原始字节。
3. **crawler 依赖声明缺项**：`requirements.txt` 缺 `greenlet`（SQLAlchemy asyncio 必需）与 `aiosqlite`。修复：改为 `sqlalchemy[asyncio]` 并补 `aiosqlite`。

### 一个"测试自身错误"（值得记录）
- 联调初版用 `fetch().text()` 校验 CSV BOM → 测试端也会剥 BOM，误判失败。改为 `arrayBuffer()` 校验原始字节 `EF BB BF`。**结论：验证 BOM 必须看字节，不能看解码后的字符串。**

# 第 16 轮 · 分布式调度（多实例下同一订阅只执行一次）

**目标**：进程内定时器在多实例部署下会重复推送。要让同一订阅在多实例下**只被执行一次**，
且实例崩溃后锁自动过期。约束：不引入 Redis，抢占必须单条 SQL 原子完成，单实例行为零回归。

### 设计
- **原子抢占**：`subscriptions.claimDue()` 用**单条条件 UPDATE** 同时完成三重判断
  （仍启用且有表达式 / 仍到期 / 无锁或锁已陈旧），靠 SQLite 写锁天然互斥，零第三方依赖。
  `locked_at` 早于 `SCHEDULER_LOCK_TTL_MS`（默认 5min）视为持有者已崩溃，可被接管。
- `scheduler.service.ts` 的 `tick()` 从「直接执行」改为「逐条 `claimDue` 抢占，抢不到就 `skipped += 1`」；
  `finally` 里 `advanceAndRelease`（成败都推进 `next_run_at` + 释放锁）。
- 实例正常退出时 `onModuleDestroy` 调 `releaseInstanceLocks(instanceId)`，避免其它实例空等 TTL。
- `notifications.service.ts` 抽出 `runRow(row, opts)`（不做归属校验），`run(userId,id)` 委托它 —— 调度器与用户接口共用同一链路。

### 本轮修掉的问题（按发现顺序）
1. **`PRAGMA journal_mode = WAL` 需要排他锁，而 `busy_timeout` 设在它之后** —— 两实例同时启动时第二个直接崩 `database is locked`。修正：`busy_timeout` 提到 WAL 之前。
2. **并发播种非幂等** —— A 已插 8 条后，B 的 `COUNT(*) = 0` 检查通过又插 8 条。修正：加 `CREATE UNIQUE INDEX idx_institutions_unique ON institutions(name, program)` + `INSERT OR IGNORE` + 统计 `inserted`。
3. **`attempt to write a readonly database`（SQLITE_READONLY，errcode 8）—— 本轮最关键的坑**
   - 现象：多实例冷启动时，一方连接被**永久**置为只读，此后**任何**写语句都失败。
   - 用临时探针（双进程各写 100 次、同时冷启动、各 6 轮）定位：
     - `journal_mode = wal`：6 轮中 3~4 轮出现一方 100/100 全失败；
       **重试同语句 0/5 无效**（粘性），**关闭并重开连接 5/5 完全恢复**，切 `delete` 也 5/5 恢复。
     - `journal_mode = delete`：**6 轮 6 次零失败**。
   - 结论：这是 `node:sqlite` + WAL 在 **Windows** 上多进程同时打开的可复现缺陷。
   - 修正（双保险）：
     1. `resolveJournalMode()` 按平台选默认 —— **Windows → `delete`、其他 → `wal`**，可用 `SQLITE_JOURNAL_MODE` 覆盖（非法值 fail fast）。
     2. `DatabaseService` 内置**只读自愈**：`run()` 与 `retryRun()` 捕获 `isReadonlyError` 时自动 `reopen()`（close + 重开）再试一次；用 `txDepth` 拦住「事务中重开」（会丢未提交更改）。
   - 复测：`delete` 5/5 轮全绿、`wal` 5/5 轮全绿（自愈兜住）。
4. **多实例测试时序性失败（测试侧缺陷，非产品缺陷）** —— `seen` 以 `tick.at` 为键，而 **Windows 时钟粒度约 15ms**，两实例同时启动的 `setInterval` 常落在同一毫秒 → 一方的 tick 被静默丢弃，导致「两个实例都跑过 tick」「执行次数合计恰好为 1」误报。
   - 修正：① 键改为 `` `${instance}:${at}` ``；② 互斥判定改用**累计计数器**而非逐轮采样。
5. **`last_result` 只保留最近一轮** —— 高频轮询仍可能漏掉「真正执行的那一轮」。修正：`SchedulerStatus` 新增累计指标 `scanned_total / ran_total / failed_total / skipped_total` 与 `busy_ticks`（`last_result` 保留作逐轮快照）。这同时是运维需要的累计观测。
6. **`waitReady` 只传了端口没传实例名**（上次编辑的遗漏）—— 改为加一张 `portToInstance` 反查表，让 `waitReady(port)` 自己解析实例，避免改调用点。

## 二、发现的真实功能缺陷（本轮最大收获）

**顿号拆分导致订阅完全失效**：网关 `subscriptions.service.ts` 的 `toJsonArray` 用 `/[,，\s]+/` 拆分，
**不含顿号「、」**；而控制台的标签写「顿号或逗号分隔」、占位符示例是 `数据分析、SQL`、编辑回显用 `.join('、')`。
用户按提示输入顿号 → 被整体当成**一个关键词** → 订阅永远匹配不到任何岗位。
修法：网关正则补 `、`；前端 `format.ts` 新增 `splitList`（覆盖 `, ， 、 空格`）并**以数组提交**；弹窗加 chips 实时预览。
教训：**界面提示文案必须与后端解析规则对齐**，否则提示本身就是误导。
