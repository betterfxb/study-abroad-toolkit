# 模块二 · 岗位库与全链路闭环

> 版本：v1.0 ｜ 对应服务：`apps/crawler` ｜ 接口契约：`docs/02-详细设计/03-接口契约.md` §6.1

---

## 一、本轮目标

模块二此前已具备：多源适配器、合规层、降级链路、抽取器（规则 + LLM 通道）、PoC 运行器。
但链路只到「抽取」为止——**岗位数据的读侧（查询 / 筛选 / 导出）完全缺失**，数据落库后无法被前端消费。

本轮补齐**读侧闭环**：采集 → 抽取 → 去重 → **入库** → **查询** → **导出汇总表**。

---

## 二、交付内容

### 1. 岗位库接口（新增）

实现位置：`app/api/jobs.py`（路由）+ `app/services/jobs_query.py`（查询逻辑）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/jobs` | 岗位列表：分页 + 筛选 + 排序 |
| GET | `/jobs/{id}` | 岗位详情（含来源文章、标签） |
| GET | `/jobs/facets` | 聚合筛选项：城市 / 公司 / 学历 / 标签 |
| GET | `/jobs/export.csv` | 导出实习信息汇总表（CSV，带 UTF-8 BOM） |

**筛选参数**：`keyword`（公司/岗位/专业/文章标题）、`city`、`company`、`education`、
`status`（active/expired/removed/all）、`min_confidence`、`date_from`、`date_to`、`has_deadline`。

**排序**：`sort=字段:方向`，支持 `published_at` / `created_at` / `deadline` / `confidence` /
`company` / `city`；非法字段与方向自动回退默认值，不报错。

**两个设计细节**：

- **稳定分页**：排序始终附加 `id desc` 作为次级键，避免同一排序值下翻页出现记录漂移/重复。
- **标准分面搜索**：`/jobs/facets` 统计某维度时排除该维度自身的筛选条件
  （例如按「深圳」筛选时，城市分面仍返回全部城市，便于用户切换筛选）。

### 2. ORM 模型跨方言化

`app/models.py` 原先硬编码 PostgreSQL 专有类型，导致无法在无 PostgreSQL 环境验证。

改为方言变体：

```python
JSONType = JSON().with_variant(JSONB, "postgresql")
BigIntPK  = BigInteger().with_variant(Integer, "sqlite")
```

- 生产（PostgreSQL）：仍生成 `BIGSERIAL` / `BIGINT` / `JSONB`，与 `db/migrations/0001_init.sql` 一致，**行为不变**；
- 本地（SQLite）：自动降级为 `INTEGER` / `JSON`，使端到端链路可在无 Docker 环境完整验证。

### 3. 全链路运行脚本（新增）

`scripts/jobs_flow.py`：与 `poc.py`（内存仓储、验证链路与指标）互补，本脚本**真实落库**并导出汇总表。

```bash
# 离线样例 → SQLite → 导出 CSV
python scripts/jobs_flow.py --sources config/poc_sources.json

# 真实公开源
python scripts/jobs_flow.py --sources config/poc_sources.real.json --only remoteok

# 指向真实 PostgreSQL
python scripts/jobs_flow.py --sources config/poc_sources.json \
    --dsn "postgresql+psycopg://user:pass@localhost:5432/qiuzhi"
```

产出：`docs/03-PoC/jobs-summary-<ts>.csv`（汇总表）、`jobs-flow-<ts>.md`（运行报告）。

### 4. 端到端测试（新增）

`tests/e2e_jobs_test.py`，用真实 SQLite 落地，覆盖：

采集入库 → 重复采集幂等 → 筛选/分页/排序/聚合/详情/CSV 导出 → FastAPI `/jobs` 系列接口（含 404 / 422）。
当前 **39 项全通过**。

## 三、本轮修掉的两个真实缺陷

### 缺陷 1：`deadline` 类型不匹配（隐蔽）

- **现象**：抽取层对外输出 `deadline` 为 ISO 字符串（`"2026-11-30"`），而 `jobs.deadline` 是 `DATE` 列。
- **影响**：PostgreSQL 靠隐式 `text→date` 转换侥幸通过；**SQLite 直接抛 `TypeError`**，
  任何按列类型严格校验的驱动都会失败。属于「换环境就炸」的潜伏问题。
- **修复**：在落库边界（`SqlRepository.save_job`）显式转换 `_to_date()` / `_to_float()`，
  保持抽取层对外契约（JSON 友好的 ISO 字符串）不变。

### 缺陷 2：单条坏数据污染整个批次

- **现象**：某条记录 flush 失败后，Session 进入「待回滚」状态，**后续所有记录连带失败**
  （实测：4 篇文章只入库 1 篇，其余全部报 `PendingRollbackError`）。
- **影响**：一个脏字段 = 整个源本轮采集几乎全部丢失，且错误信息互相掩盖，难以定位。
- **修复**：`SqlRepository` 增加 `item_scope()`（`SAVEPOINT`），`Pipeline` 对每条记录包裹该作用域。
  失败只回滚该条，其余记录正常入库。

> 两个缺陷都是本轮引入端到端测试后**立即暴露**的——此前只有内存仓储的冒烟测试覆盖不到数据库边界。
