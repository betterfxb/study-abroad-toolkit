# 模块二 · 抽取器对比结论（规则 vs LLM）

> 版本：v1.0 ｜ 评测脚本：`apps/crawler/scripts/compare_extractors.py`
> 基准集：`samples/benchmark/cases.json`（基础集 8 例）、`samples/benchmark/cases.hard.json`（难例集 6 例）
> 评测口径：核心 6 字段（公司 / 岗位 / 城市 / 薪资 / 截止日期 / 投递方式）逐字段对比人工标注

---

## 一、结论速览

| 基准集 | 用例数 | 规则抽取 | LLM 抽取 |
| --- | --- | --- | --- |
| 基础集（标签规范 / 常见写法） | 8 | **100.0%** | 待跑（缺 API Key） |
| 难例集（真实自由形态） | 6 | **48.5%** | 待跑（缺 API Key） |
| 合并 | 14 | **78.2%** | 待跑（缺 API Key） |

**核心判断**：规则抽取在**结构化程度高**的文本上已经够用（基础集满分），但在**真实自由文本**上只能拿到约一半字段——缺口集中在「表格 / 英文 / 括号城市 / 后缀式截止 / 时薪周期推断」。这部分正是 LLM 抽取的价值区间。

---

## 二、评测方法（为什么分两套集）

单一基准集无法得出可信结论：

- 如果只跑**基础集**（本轮开发时按规则能力构造的规范文本），规则 100%、LLM 也大概率接近 100%，**没有区分度**；
- 如果只跑**难例集**（全部是规则够不到的自由形态），又无法说明规则本身的能力边界在哪。

因此拆成两套：

| 集合 | 设计目标 | 典型形态 |
| --- | --- | --- |
| **基础集** | 验证规则能力、作为回归基线 | `【公司】X`、`公司：X`、`Location: X` 等标签式文本 |
| **难例集** | 暴露规则天花板、体现 LLM 增量 | TSV 表格、编号列表、英文、长软文、时薪、母公司+事业群 |

> 说明：基础集的 8 个用例在开发过程中被用于驱动规则迭代（这是正常的回归驱动），难例集则是**按真实公众号 / 平台形态独立构造**、未针对规则做调优，用于公平对比。

## 四、失败归因分类

### A. 规则**不可**解决 → 必须 LLM

| 类型 | 用例 | 现象 | 为什么规则做不到 |
| --- | --- | --- | --- |
| 表格结构 | h01 | 表头「公司\t岗位\t地点…」被当成公司值 | 规则按行/标签匹配，无表格语义 |
| 英文文本 | h03 | 0/6，整篇无中文标签 | 标签体系是中文（+少量英文标签），自由英文无锚点 |
| 时薪周期 | h05 | `25元/小时` → 抽成 `25元/天` | 需理解「按小时结算，每小时 25 元」的语义，规则默认日薪 |
| 无关键词截止 | h05 | `12 月 5 日前有效` → 空 | 无「截止/截至」关键词，规则无触发点 |
| 后缀式截止 | h06 | `11 月 28 日截止` → 空 | 规则要求「标签+值」，此处是「值+标签」倒装 |
| 母公司+事业群 | h06 | `腾讯` → 抽成 `事业群面向在校生` | 公司名被空格切开，规则只能取连续片段 |
| 句内城市 | h04/h06 | `位于深圳南山`/`在深圳办公` → 空 | 无「地点/base」标签，纯语境 |

### B. 规则**可**解决 → 已修 / 待修

| 类型 | 状态 | 说明 |
| --- | --- | --- |
| 无标签「X在招Y」句式 | ✅ 已修 | `_COMPANY_ACTION`，覆盖公众号高频写法 |
| 括号块公司 `【腾讯】` | ✅ 已修 | `_bracket_company`，排除标签用语 |
| 裸薪资 `200元/天`/`180 块` | ✅ 已修 | `_SALARY_BARE` |
| 行内截止 `截止 11-25` | ✅ 已修 | `_DEADLINE_IN`（放开行首锚点） |
| 管道分隔城市 `｜深圳｜` | ✅ 已修 | `_pipe_city` |
| 行内 `base 上海` | ✅ 已修 | `_CITY_IN` |
| 长句标题起点（h04） | ⏳ 待定 | 需更强的边界判定，收益/成本比一般，倾向交给 LLM |

> 说明：A 类为**语义 / 结构理解**问题，规则方案要么做不到、要么会引入大量脆弱特判；B 类为**写法变体**问题，用通用规则批量覆盖性价比高，已全部落地并通过回归。

## 五、LLM 侧状态

LLM 抽取的**代码链路已就绪**（`app/llm/client.py` 统一客户端 + 任务路由 + 失败自动降级），但**本轮未取得 API Key，未执行对比**。

脚本在缺 Key 时会明确提示并自动只跑规则抽取：

```
警告：--llm 已指定，但未检测到 LLM_API_KEY。
      请先设置环境变量后重跑 …
```

启用方式（拿到 Key 后一条命令即可产出完整对比）：

```bash
# bash
export LLM_API_KEY=sk-xxx
python apps/crawler/scripts/compare_extractors.py --set all --llm

# PowerShell
$env:LLM_API_KEY='sk-xxx'
python apps/crawler/scripts/compare_extractors.py --set all --llm
```

预期：难例集（尤其 h01/h03/h04/h06）应有显著提升；基础集应保持或接近满分。

## 六、生产策略建议：混合抽取（规则兜底 + LLM 增强）

基于本轮数据，建议**不做二选一**，而是分层：

```
正文 → [LLM 可用?]
        ├─ 是 → LLM 抽取（覆盖自由文本，难例集为主要收益来源）
        │        └─ 失败/超时 → 落到规则
        └─ 否 → 规则抽取（零依赖、零成本、离线可跑）
                 └─ 置信度低（字段少）→ 标记「待人工补全」
```

理由：

1. **成本**：规则零调用成本，适合全量初筛；LLM 按需触发（如仅对规则低置信度的文章调用）。
2. **可用性**：LLM 不可用时链路不断（这是既有的降级设计，本轮验证有效）。
3. **质量**：规则在标签式文本上已达 100%，无需浪费 LLM 调用；把 LLM 预算集中在难例形态上。
4. **置信度**：规则按字段填充度推导置信度（0.35 + 0.08×填充数，上限 0.90），可直接作为「是否升级到 LLM」的开关。
