## 0. 项目背景与产品形态基准

### 0.1 参考产品拆解（求职方舟AI）

| 维度 | 现状 |
|---|---|
| 产品形态 | 官网（工具集）+ **Chrome/Edge MV3 浏览器插件** |
| 首页结构 | 11 张工具卡片网格，每卡含图标 / 标题 / HOT 标签 / 使用人数 / 一句话描述 |
| 核心卖点 | 「AI 填网申」——插件自动识别企业官网简历表单，一键填充，30 分钟 → 3 分钟 |
| 自述能力边界 | 识别 **70%** 官网、填充 **80%** 字段，**不做自动提交**，人工复核后由用户提交 |
| 关键机制 | 简历一键解析、字段智能识别、智能记忆填写（简历外字段填一次即记忆）、专岗简历美化 |
| 用户信任设计 | 创始人手记（"小风学长"）叙事 + 使用人数社会认同 + 使用文档 |
| 数据类工具 | 校招/实习网申汇总表、投递进展表、笔试真题表（在线 Excel 形态） |

### 0.2 视觉与交互基准（需继承）

- **卡片式工具集首页**：图标 + 标题 + 标签 + 人数 + 一句话描述，栅格布局，圆角卡片、轻阴影。
- **一句话价值主张**：每个工具一句人话描述，降低理解成本。
- **社会认同前置**：使用人数、HOT 标签。
- **人味叙事**：创始人手记 / 使用场景痛点铺陈（"投 50 家又要重复 50 遍"）。
- **插件侧 UI**：页面右下角悬浮按钮 + 展开式操作浮窗（简历版本切换、预览编辑、播放启动）。
- **表格类产品**：在线 Excel 形态的汇总表 / 进展表，实时更新。

> 结论：新项目沿用「官网工具集 + 浏览器插件 + 在线表格」三件套形态，视觉延续卡片化、人话文案、社会认同三条原则即可，无需重新设计语言。

## 一、模块一：海外研究生留学网申自动填写

### 1.1 与「求职网申自动填写」基线逐项对比

#### 1.1.1 对比总览

| 对比项 | 求职网申（基线） | 留学研究生网申 | 差异等级 |
|---|---|---|---|
| 主战场 | 企业自建/北森/Moka/牛客/Workday 等 | ApplyWeb、Liaison、Slate 三大平台 + 各校自研 | **高** |
| 表单结构 | 单页长表单或多步，步骤少（2–4 步） | **几乎全是多步向导**（5–12 步），步骤强依赖 | **高** |
| 字段标准化 | 中高（国内招聘字段趋同） | 低（同一字段不同平台命名/格式各异） | **高** |
| 动态字段 | 少量 | **大量**（选学位类型/项目后动态展开） | **高** |
| 附件上传 | 仅简历 PDF | **多附件**：成绩单/PS/CV/推荐信/写作样本 | **高** |
| 第三方协作 | 无 | **推荐人邀请**（跨邮箱、外部提交） | **高** |
| 人机验证 | 少 | reCAPTCHA / hCaptcha / Cloudflare Turnstile 常见 | 中 |
| 登录态 | 企业账号注册登录 | 学校账号 + 邮箱验证链接 | 中 |
| 自动化容忍度 | 中等 | **ToS 普遍更严格**（教育公平/反代填） | **高** |

#### 1.1.2 表单结构差异

- **求职**：多为单页长表单，或 2–4 步轻量向导；字段顺序基本线性，无强状态依赖。
- **留学**：**多步向导为主流**，典型步骤链：
  `Program Selection → Personal Info → Address → Education History → Test Scores → Recommenders → Essays → Documents Upload → Review → Fee`
  - 每步独立提交（Save & Continue），草稿状态**服务端持久化**（关掉浏览器再回来仍在原步）。
  - **动态字段**：选择学位类型（MS/PhD）、项目、国际生身份后，后续步骤的字段集合会变化。
  - **SPA 路由**：部分平台（尤其 Slate）为单页应用，步骤切换不刷新页面，DOM 增量更新。

#### 1.1.3 字段类型差异

| 字段类别 | 求职网申 | 留学网申 | 迁移影响 |
|---|---|---|---|
| 基础文本 | 姓名/手机/邮箱 | 姓名（Last/First/Middle 分离）、**护照名**、Preferred Name | 需字段拆分与顺序适配 |
| 下拉 | 学历/专业/城市 | 国家、州（US 50 州）、学位类型、项目、母语、签证类型 | 选项量大、**州列表需内置** |
| 日期 | 统一 YYYY-MM | **US `MM/DD/YYYY` vs UK `DD/MM/YYYY` 混用** | 需区域格式识别 |
| 地址 | 单层 | **多级**：Street / City / State / Postal / Country，含邮编格式校验 | 需结构化地址模型 |
| 特殊字段 | GPA（百分制） | **GPA 多制式**：4.0 / 100 / UK 等级（First、2:1）；需**换算表** | **新增能力** |
| 语言/标化 | 无 | **TOEFL/IELTS/GRE/GMAT/Duolingo**：总分 + 分项 + 考试日期 + Registration ID | **新增能力** |
| 教育经历 | 单段 | **多段可增删**，每段含学校/学位/专业/起止/GPA | 需动态列表组件 |
| 推荐人 | 无 | **3 位**：姓名/头衔/机构/邮箱/关系 | **新增能力** |
| 文书 | 无（或附件） | **PS/SOP 直接粘贴文本框**，硬性字数限制 | 需字数实时校验 |
| 附件 | 简历 1 份 | 成绩单/PS/CV/推荐信/写作样本/作品集 | **多附件 + 格式校验** |

#### 1.1.4 分步与保存回填流程差异

- **求职**：填错可整页重来，无强状态；回填主要靠"智能记忆"。
- **留学**：
  - **每步必须先 Save 才能进入下一步**，存在服务端草稿态；
  - 返回上一步修改后，后续步骤可能被**重置或需重新确认**；
  - **字段回填依赖草稿 API**，不能简单靠前端记忆；
  - 断点续填是刚需：用户可能分多天完成一份申请。

#### 1.1.5 文件上传差异

| 材料 | 常见格式 | 常见大小限制 | 备注 |
|---|---|---|---|
| 成绩单 Transcript | PDF | ≤ 5–10 MB | 部分要求官方寄送/官方电子送分 |
| PS / SOP | PDF / DOCX | ≤ 2–10 MB | 常同时要求文本框粘贴 |
| CV / Resume | PDF | ≤ 2–5 MB | 与求职简历结构不同（学术向） |
| 推荐信 | 由推荐人上传 | — | **申请人只填推荐人信息，不接触信件本体** |
| 语言成绩 | 官方送分为主 | — | ETS/IELTS 官方送分；部分接受扫描件 |

> 关键点：上传控件大量使用**自定义拖拽区**（非原生 `<input type=file>`），需通过 `DataTransfer` 构造 `FileList` 并派发 `drop`/`change` 事件，**不能直接赋值**。

#### 1.1.6 登录态与人机验证

- **登录态**：学校账号注册 + **邮箱验证链接**（无法绕过，需用户自行完成首次注册验证）。
- **人机验证**：注册/登录/提交环节常见 **reCAPTCHA v2/v3、hCaptcha、Cloudflare Turnstile**。
- **合规红线**：教育申请属高诚信场景，**不得破解验证码、不得自动提交、不得代签声明**。产品定位必须是"辅助填写，用户本人操作并复核"。

#### 1.1.7 可复用能力 vs 需重构部分

**可直接复用（约 60% 底座）**
1. **浏览器插件底层**：MV3 架构、content script 注入、悬浮按钮 UI、事件派发基础。
2. **字段识别与映射引擎**：label/aria/name/placeholder/邻近文本的多信号识别 + LLM 语义匹配。
3. **规则引擎**：字段词典 + 映射规则 + 优先级决策。
4. **资料解析**：PDF/DOCX 简历解析、结构化 Profile 生成。
5. **智能记忆**：历史填写学习与复用。
6. **Profile 存储与同步**：用户资料库、加密存储、多端同步。

**需重构 / 新增（约 40% 上层）**
1. **留学字段体系**：GPA 换算、语言/标化成绩、Education History 多段、推荐人、护照信息。
2. **多步向导控制器**：步骤遍历、Save & Continue、草稿态回填、断点续填、动态字段重扫。
3. **多附件上传**：拖拽区注入、格式/大小前置校验、多材料槽位映射。
4. **平台适配层**：ApplyWeb / Liaison / Slate 三大体系 + 各校自研的差异化适配。
5. **院校特有字段**：每校自定义问题（Why this program 等）与自定义文书题。
6. **推荐人邀请流程**：跨邮箱外部协作，插件无法介入 → 转为"引导 + 状态跟踪"能力。
7. **区域化格式**：日期格式、地址层级、姓名顺序、州/国列表。

### 1.2 实现思路与架构分层

```
┌──────────────────────────────────────────────────────────────┐
│ L5 应用层   Web 控制台（资料管理/材料库/进度跟踪） + 插件浮窗 UI   │
├──────────────────────────────────────────────────────────────┤
│ L4 数据层   Profile库 · 字段词典/映射规则库 · 平台适配规则库      │
│             · 材料库 · 填写日志与效果数据                        │
├──────────────────────────────────────────────────────────────┤
│ L3 智能决策层（服务端）                                          │
│   字段语义匹配(LLM+Embedding+规则) · 平台适配路由 · GPA换算       │
│   · 文书微调(可选) · 字数校验                                    │
├──────────────────────────────────────────────────────────────┤
│ L2 通信层   插件↔服务端(HTTP/WebSocket) · chrome.storage 本地缓存 │
├──────────────────────────────────────────────────────────────┤
│ L1 采集执行层（浏览器插件 MV3）                                   │
│   PageSense 页面感知 → FieldExtractor 字段抽取 →                 │
│   StepController 步骤控制 → Filler 填充执行 → Validator 回读校验  │
└──────────────────────────────────────────────────────────────┘
```

**核心流程**
1. `PageSense` 判定当前是否申请表单页 → 激活悬浮按钮。
2. `FieldExtractor` 扫描当前步骤 DOM，产出「字段清单 + 语义候选」。
3. 上报 `L3`，`AdapterRouter` 识别平台/院校 → 加载对应适配规则。
4. `FieldMatcher` 将字段与 Profile 匹配（LLM + 词典 + 规则三级兜底），返回填充指令。
5. `Filler` 按字段类型执行差异化写入（受控组件原生 setter、下拉真实点击、日期选择器、富文本、文件注入）。
6. `Validator` 回读校验；`StepController` 触发 Save & Continue 并进入下一步，循环至末步。
7. 汇总未填/低置信字段，交由用户人工复核后**由用户自行提交**。

### 1.3 关键技术选型及理由

| 层次 | 选型 | 理由 |
|---|---|---|
| 插件 | Chrome/Edge MV3（与基线一致） | 复用基线底层，覆盖目标用户主流浏览器；Firefox 后续排期 |
| 字段抽取 | 多信号融合（label/aria/name/placeholder/邻近文本）+ 轻量视觉特征 | 单一信号在异构表单上失效率高，多信号显著提升召回 |
| 字段匹配 | LLM（主）+ Embedding 检索字段词典（快）+ 规则引擎（兜底） | 平衡准确率、成本、延迟；规则兜底保证高频字段稳定 |
| 表单写入 | 原生 setter + `input/change/blur` 事件派发；下拉用真实点击序列 | 主流框架（React/Vue）受控组件必须走原生 setter 才能被识别 |
| 文件上传 | `DataTransfer` 构造 `FileList` + `drop/change` 事件 | 自定义拖拽区唯一可行的注入方式 |
| 步骤控制 | 状态机 + 每步 DOM 重扫 | 适配 SPA 增量渲染与动态字段 |
| 服务端 | Node.js（NestJS/Express）+ Python（FastAPI）双服务 | Node 扛实时通信与规则服务，Python 扛 LLM/解析/换算 |
| 存储 | PostgreSQL + Redis | 关系型存 Profile/规则/日志；Redis 做缓存与任务队列 |
| 文件 | 对象存储（OSS/COS） | 材料文件托管，加密 + 权限隔离 |
| 验证码 | **不破解**，检测到即暂停并引导人工 | 合规底线，避免 ToS 与法律风险 |

### 1.4 主要风险与应对

| 风险 | 等级 | 应对措施 |
|---|---|---|
| 平台长尾差异巨大，适配成本失控 | **高** | 「通用 LLM 识别 + 头部平台适配器」策略：优先吃透 ApplyWeb/Liaison/Slate，长尾靠通用识别兜底，不逐校硬编码 |
| 多步向导状态丢失/回滚 | 高 | 每步 Save 后校验草稿；断点续填走草稿 API；返回修改后重扫后续步骤 |
| 人机验证拦截 | 中 | 检测到验证码即暂停、提示人工完成；不提供任何绕过能力 |
| ToS / 教育诚信合规 | **高** | 定位为"辅助填写工具"，**不自动提交**、不代签声明；产品内明确提示用户复核与自主提交 |
| 敏感数据（护照/成绩单）泄露 | **高** | 端到端加密、最小化上传、敏感字段本地优先、权限隔离与审计日志 |
| 动态字段导致漏填 | 中 | 步骤切换后强制重扫；对新增字段二次匹配 |
| 申请季流量峰值（9 月–次年 1 月） | 中 | 提前完成 PoC 与压测；服务端弹性扩容；错峰调度 LLM 调用 |
| 文书字数/格式校验不严 | 低 | 前端实时字数统计 + 提交前硬校验 |

### 1.5 需你提供的资料清单

1. **目标申请系统页面样例或操作录屏**：ApplyWeb / Liaison / Slate 各至少 1–2 个完整申请流程录屏（含注册、多步填写、上传、推荐人设置）。
2. **目标院校与项目列表**：Top 20–50 所，标注各自使用的申请平台（用于排适配优先级）。
3. **字段映射规则**：现有「求职网申」的字段词典与映射规则文件（作为迁移起点）。
4. **测试账号**：各目标平台至少 1 个可登录的测试账号（含已通过邮箱验证的账号）。
5. **申请材料模板**：成绩单 / PS / SOP / CV / 推荐信的样例文件，含各校**格式与大小限制**说明。
6. **Profile Schema 清单**：明确"要填哪些字段"的完整字段清单（含 GPA 制式、语言成绩分项、教育经历字段）。
7. **合规口径**：法务对"辅助填写、不自动提交"边界的书面确认（如有）。

### 1.6 分阶段开发排期建议

| 阶段 | 周期 | 目标 | 里程碑 | 验收标准 |
|---|---|---|---|---|
| **P0 可行性 PoC** | 2 周 | 打通"识别→填充→多步→上传"最小闭环 | 3 个代表平台（ApplyWeb/Liaison/Slate）各完成 1 份申请表单自动填充 | 字段填充率 ≥ 60%；多步可连续推进；至少 1 类附件成功注入 |
| **P1 留学能力层** | 3 周 | 留学专属字段 + Profile 库 + 附件上传 | 字段词典 v1、GPA 换算服务、材料库上线 | 语言成绩/教育经历/推荐人字段填充率 ≥ 80%；多附件格式校验准确 |
| **P2 多平台适配** | 3 周 | 平台适配器扩到 10–15 所院校 | 适配规则库 v1 + 推荐人流程引导 | 覆盖院校识别率 ≥ 80%；单校填写时间 < 5 分钟 |
| **P3 稳定化与灰度** | 2 周 | 稳定性、监控、灰度发布 | 监控看板 + 灰度上线 | 崩溃率 < 1%；误填率 < 2%；零自动提交事故 |

**模块一总工期建议**：10 周（含 PoC），其中 PoC 结果决定是否继续投入。

## 二、模块二：实习信息自动爬取

### 2.1 数据源与获取路径评估

| 路径 | 说明 | 稳定性 | 风险 | 建议 |
|---|---|---|---|---|
| **微信公众平台历史文章接口**（`mp.weixin.qq.com/mp/profile_ext`） | 需登录态 cookie（`__biz`/`key`/`pass_ticket`/`uin`），`key` **时效短（数小时–1 天）** | **低** | 严格限流、易封号、参数易失效 | **不作为主源** |
| **搜狗微信搜索**（weixin.sogou.com） | 聚合搜索入口 | **低** | 验证码、封 IP、已大幅收紧 | 仅作补充 |
| **第三方数据服务**（新榜/清博/西瓜数据/微小宝） | 付费 API，提供公众号历史文章与元数据 | **高** | 成本、依赖供应商 | **推荐主源 A** |
| **RSS 中转**（wechat2rss / WeRSS / RSSHub 部分支持） | 第三方把公众号转 RSS | **中** | 依赖第三方存活、覆盖有限 | 针对固定关键号自建，作补充 |
| **企业号 / 官网招聘页** | 直接抓企业官网招聘页或企业微信 | **高** | 覆盖有限 | **推荐主源 B（兜底）** |
| **招聘平台转载**（实习僧、牛客、应届生、Boss 实习） | 结构化岗位数据 | **高** | 部分需授权/合作 | **推荐主源 C** |
| 微信"搜一搜" / 搜索引擎收录 | 人工检索入口 | 低 | 不可编程、覆盖随机 | 不采用 |

**核心结论**：微信公众号**历史文章接口不可作为唯一主源**——技术上可行但稳定性差、合规与封号风险高。应采用**多源混合架构**。

### 2.2 实现思路与架构分层

```
┌──────────────────────────────────────────────────────────────┐
│ L6 监控层   任务监控 · 失败告警 · 频控看板 · 数据质量抽检         │
├──────────────────────────────────────────────────────────────┤
│ L5 服务层   搜索/筛选 API · 订阅推送 · 后台管理 · 降级开关        │
├──────────────────────────────────────────────────────────────┤
│ L4 存储层   PostgreSQL(文章/岗位/源) · Redis(队列/缓存)          │
│             · 对象存储(封面/附件) · (可选)向量库(语义去重/匹配)    │
├──────────────────────────────────────────────────────────────┤
│ L3 处理层   去重(SimHash/指纹) · 字段标准化 · 分类打标 · 质量校验  │
├──────────────────────────────────────────────────────────────┤
│ L2 解析层   正文抽取(readability/trafilatura) + LLM 结构化抽取    │
├──────────────────────────────────────────────────────────────┤
│ L1 采集层   调度器 · 采集器(HTTP/Playwright) · 代理池/账号池      │
│             多源适配器：第三方API / RSS / 招聘平台 / 企业官网      │
└──────────────────────────────────────────────────────────────┘
```

**降级替代方案（分级）**
- **L0 全自动多源**：第三方 API + 招聘平台 + 官网，日更。
- **L1 降级**：第三方 API 失效 → 切换到自建 RSS + 官网抓取，覆盖度下降但不断流。
- **L2 降级**：全部自动源失效 → 半自动：运营人员把公众号文章转发至统一入口（企微/邮箱/表单），系统只做解析入库。
- **L3 兜底**：纯人工订阅 + 表格维护（沿用参考产品的"在线汇总表"形态）。

### 2.3 关键技术选型及理由

| 层次 | 选型 | 理由 |
|---|---|---|
| 采集 | Python `httpx`（静态）+ `Playwright`（渲染型） | 覆盖 API/静态页/JS 渲染页三类；Scrapy 用于规模化扩展 |
| 调度 | Celery / APScheduler（轻量起步），后期 Airflow | 起步轻量，规模上来后转 DAG 编排 |
| 反爬 | 代理池 + UA 池 + 低频随机间隔 + 账号池（**合规前提下**） | 降低封禁概率，而非对抗性突破 |
| 正文抽取 | `trafilatura` / `readability-lxml` | 公众号正文结构较规整，抽取准确率高 |
| 结构化 | LLM 抽取（岗位字段） | 正文非结构化，LLM 抽取显著优于正则 |
| 去重 | SimHash + 归一化指纹 | 成本低、效果好；跨源去重靠指纹对齐 |
| 存储 | PostgreSQL + Redis + 对象存储 | 关系型存结构化数据，Redis 做队列/缓存 |
| 向量库（可选） | pgvector / Milvus | 语义去重与岗位匹配，二期引入 |

**抓取字段定义**

| 层级 | 字段 |
|---|---|
| 文章级 | 标题、公众号名、发布时间、原文链接、封面图、正文摘要、阅读/点赞（可选） |
| 岗位级（正文抽取） | 公司、岗位名、城市、实习时长、日薪/月薪、学历要求、专业要求、投递方式（邮箱/链接/二维码）、截止时间、留用机会、标签 |
| 元数据 | 抓取时间、来源渠道、去重指纹、置信度 |

**更新频率**：公众号源每日 1–3 次（低频错峰）；招聘平台每日 1 次；企业官网每日 1 次。

**存储结构（核心表）**
- `sources`（源配置：类型/频率/凭证/状态）
- `articles`（文章：URL 唯一键、标题、公众号、时间、正文、指纹）
- `jobs`（岗位：归属文章、公司、岗位、城市、薪资、要求、投递方式、指纹）
- `crawl_log`（抓取日志：任务、耗时、成功/失败、限流记录）
- `dedup_index`（去重索引：指纹 → 主记录 ID）

**去重策略（三级）**
1. **文章级**：`URL 唯一键` + `标题+公众号+日期` 的 SimHash 比对。
2. **岗位级**：`公司+岗位名+城市+薪资` 归一化后生成指纹；正文 SimHash 相似度 > 0.9 判重。
3. **跨源级**：同一岗位多源出现 → 保留**最早 + 最权威源**，其余标记为引用来源。

### 2.4 主要风险与应对

| 风险 | 等级 | 应对措施 |
|---|---|---|
| 微信接口封号 / 封 IP | **高** | 不做主源；若自建采集则严格低频、随机间隔、代理池、账号池轮换 |
| 接口 `key` 时效失效 | 高 | 自动刷新机制 + 失效即切源；多源冗余 |
| 第三方服务依赖 | 中 | 多供应商备份 + 自建 RSS 兜底 + 降级开关 |
| 法律合规（《网络安全法》《数据安全法》《个人信息保护法》） | **高** | 仅采集**公开信息**；遵守 robots；控制频次不造成服务压力；不采集个人隐私；**署名来源、可下架**；避免《刑法》285 条风险 |
| 版权（文章版权归原作者） | **高** | 只存摘要 + 原文链接，**不整篇转载**；标注来源；提供权利人下架通道 |
| 数据质量（正文非结构化、字段缺失） | 中 | LLM 抽取 + 置信度阈值 + 人工抽检 + 字段完整率监控 |
| 岗位信息时效（过期/招满） | 中 | 记录截止时间，过期自动下架；定期回访校验 |
| 覆盖度不足（源失效导致漏采） | 中 | 覆盖率监控 + 降级链路 + 源健康度评分 |

### 2.5 需你提供的资料清单

1. **目标公众号列表**：名称 + 微信号/`__biz`，建议 20–50 个（按行业/城市分类）。
2. **第三方数据服务情况**：是否已有新榜/清博/西瓜数据等账号或预算。
3. **目标岗位类型与筛选规则**：行业、城市、岗位类别、硬性过滤条件。
4. **企业官网 / 招聘平台账号或 API 权限**：如实习僧、牛客等是否有合作或开放接口。
5. **数据合规要求**：是否允许存储原文、是否需要授权、是否需下架通道。
6. **IT 资源**：可用服务器、代理池、账号池现状（用于评估自建采集可行性）。
7. **半自动入口约定**：若走降级方案，运营人员统一转发入口（企微群 / 邮箱 / 表单）的确定。

### 2.6 分阶段开发排期建议

| 阶段 | 周期 | 目标 | 里程碑 | 验收标准 |
|---|---|---|---|---|
| **P0 源调研与 PoC** | 1 周 | 验证多源可行性 | 3 个公众号 + 1 个第三方 API + 1 个招聘平台跑通 | 单源可稳定取数 ≥ 3 天不断流 |
| **P1 采集框架** | 2 周 | 采集 + 去重 + 存储 + 调度 | 多源适配器 v1、去重引擎、调度上线 | 日更覆盖率 ≥ 70%；去重准确率 ≥ 95% |

## 三、总体可行性结论与优先推进顺序

### 3.1 可行性结论

| 模块 | 技术可行性 | 合规风险 | 落地难度 | 结论 |
|---|---|---|---|---|
| 海外研究生网申自动填写 | **可行**（底座复用 60%） | 中高（教育诚信/ToS） | 高（长尾适配重） | **有条件可行**——必须先做 PoC，且产品定位严格限定为"辅助填写、不自动提交" |
| 实习信息自动爬取 | **可行** | 高（数据合规/版权） | 中（多源+降级） | **可行**——放弃"死磕微信接口"，采用多源混合 + 分级降级 |

### 3.2 优先推进顺序

1. **第一优先｜模块二 · 实习信息自动爬取**
   - 理由：数据底座，可独立交付，风险可控，1 周即出 PoC、6 周出 MVP，见效快。
   - 关键动作：先锁定第三方数据服务 + 2–3 个核心公众号 + 1 个招聘平台，验证多源稳定性。

2. **第二优先｜模块一 · 网申自动填写 PoC（并行启动）**
   - 理由：核心差异化能力，但长尾适配重、合规敏感，**先花 2 周验证 3 个代表平台**，用数据决定是否规模化投入。
   - 关键动作：拿到 3 个平台录屏 + 测试账号，跑通"多步 + 附件 + 字段匹配"最小闭环。

3. **第三优先｜模块一 · 多平台规模化适配**
   - 前置条件：PoC 验收达标（字段填充率 ≥ 60%）。
   - 关键动作：按院校-平台映射排优先级，分批扩适配器。

### 3.3 一句话总纲

> **先把数据拿到手（模块二，快），再把最难的自动化验证清楚（模块一 PoC，稳），最后才规模化铺开（模块一适配，准）。**

### 3.4 待决策事项（需你拍板）

1. 模块二是否投入预算采购第三方数据服务（决定主源路线）。
2. 模块一 PoC 的目标平台与院校清单（决定 2 周 PoC 的范围）。
3. 合规口径是否需法务出具书面确认（建议：需要，尤其模块一）。
4. 两个模块的负责人与资源投入比例（建议：模块二 40%，模块一 60%）。
